### 一些基本概念

- ECMP（Equal-Cost Multi-Path，等价多路径路由）：当交换机或路由器到达同一个目的地有多条代价相同的路径时，它会把流量分散到这些路径上，而不是只用其中一条。

### Converged Ethernet

- 把过去分别跑在不同专用网络上的几类流量，合并到同一张以太网上传输。
- 例如，把普通以太网的TCP/IP业务流量，存储网络与HPC网络都用同一个以太网传输
- VLAN 标签是以太网帧在特定情况下额外加入的一个 4 字节字段，用来标明这个帧属于哪个 VLAN。以太网帧的 VLAN 标签里有一个 3 位字段，叫 PCP（Priority Code Point），取值 0–7。它本质上是一个流量类别编号，交换机按这个编号、经过映射表把帧分到对应的队列里，每个队列有自己独立的少量缓冲，也可以从公共缓冲中借用一定量的缓冲，可以给不同队列分配不同的带宽，也可以独立指定是否开启PFC(priority flow control).
- PFC(priority flow control)
  - 缓冲区队列涨到暂停阈值时时，开启 PFC 的队列向上游发 PAUSE 帧，不开启的队列直接丢帧。
- 通常做法是把 RoCE 流量放在一个开启 PFC 的无损优先级里，普通 TCP 流量留在不开 PFC 的有损优先级里。同一张以太网上，同时跑有损和无损两类流量。有损与无损的所有帧都落在 0–7 这 8 个类别中的某一个里。

### RDMA

- remote direct memory access
- RDMA是网卡不经过对方CPU直接读写远端内存的一种能力。
- 有多种实现，例如InfiniBand, RoCE, iWARP等

### RoCE

- RoCEv1
  - 在以太网数据链路层的L2 headers上面直接加上InfiniBand的传输层header。它没有IP头，因此不能跨越子网路由。
- RoCEv2
  - 添加了IP/UDP L3 headers，加ip头是为了支持数据中心内部与不同数据中心之间的路由，加UDP头是为了兼容现有的以太网设备，例如交换机可以依据UDP位置读源端口号，进行ECMP分流等(RoCE的目的端口全是4791,源端口可以不同)。
- 由于RoCE采用了InfiniBand的传输层，需要包按照顺序送达，以及go-back-n的重传机制(一个包传输失败，那么后面传输成功的包也不要了，直接从那个传输失败的包开始重传)。包按顺序送达的要求让多路径负载均衡变得困难。
- 拥塞控制
  - RoCEv2的拥塞控制利用了IP’s Explicit Congestion Notification (ECN)信号。交换机拥塞以后，在包上做一个记号，然后接收方再把拥塞信息传递给发送方，让发送方减速。
- 链路层流控
  - RoCE用PFC, 作用于单跳，相邻的设备之间，之前介绍过了。
  - InfiniBand与RoCE不同，它 用 credit：接收方事先告诉发送方还有多少空间，发送方只在有 credit 时才发。它是主动的，从根本上不会溢出。(发送方手里的 credit + 链路上正在去的数据 + 接收方缓冲里还没转发走的数据 + 链路上正在回来的 credit=分配的全部缓冲)

### PFC与ECN的区分

- PFC : 队列涨到暂停阈值时，交换机向上一跳发 PAUSE，作为不丢包的兜底；阈值之上预留的缓冲用来接住 PAUSE 生效前仍在路上的包；ECN: 交换机开始拥塞时就给包打标记，接收方把拥塞信息回传给发送方，让发送方降速。

### 通信模式

- Incast (IN)

  - 大量发送方向同一个进程发送包，并且这种发送是随机性无组织的。这种通信模式可能造成拥塞

  - 当通信量小于带宽与延迟的乘积时，拥塞控制无法在通信结束前通知到发送方。

- Oblivious bulk synchronous (OBS)

  - Oblivious指通信模式与具体的数据无关，仅仅与小的超参数有关
  - bulk synchronous：批量同步

- Latency-sensitive (LS)

### RoCE的问题

- Priority Flow Control (PFC) 需要大量的buffer
  - 考虑到PAUSE消息的传输延迟，交换机必须有足够的缓冲，接受这个延迟时间内发送方发过来的包，从而造成缓冲空间的浪费。而缓冲空间的释放可以降低交换机芯片的价格，或者，多出来的缓冲空间可以用于吸收瞬时的突发。
- Victim flows, congestion trees, PFC storms, and deadlocks
  - Victim flows: 对于被分配到同一个流量类别编号的不同流，只要其中有一个流填满了buffer，其他所有流都不能通了。
  - congestion trees/PFC storms: 拥塞一路逆着链路向上游传播
  - deadlocks: 如果路由使交换机缓冲之间的等待关系形成了环，那么当环上的缓冲都被占满时，每台交换机都要等下一跳空出位置才能发包，而下一跳也在等它自己的下一跳。这样环上的每一个发送方都停止发包，谁的缓冲都空不出来。
- Go-back-N的重传机制
  - 按序传输，丢包之后从那个丢的包开始重新传输，后面的包就算送到了也不要了，全部重新传输一遍。浪费资源。
  - 不支持多路径与乱序交付
- 拥塞控制
  - ECN 只有一个"是否拥塞"的二值标记，信息太粗，发送方要经过很多个 RTT 才能调到合适的速率。
  - 普通数据中心交换机的缓冲区都比较大，从而可以减少丢包概率。因为这种传输的端到端延迟比较长，往往难以很快地通知发送方降速，难以做成无损，所以只能稍微把缓冲做大一点来减少丢包。
  - HPC 机房通常用浅缓冲 + 无损网络，以减小排队延迟和丢包重传的代价。无损由链路级流控保证（如 InfiniBand 的 credit）；同时机房内线缆短、每跳所需预留缓冲小，拓扑直径小、拥塞控制反应快、队列不易堆高，因此浅缓冲就够用，也降低了交换机成本。
  - RoCE的缓冲浪费
    - lossless要求，会提前锁住一部分缓冲，在触发PFC的时候还能不丢包。这部分缓冲平时都是浪费没使用的。
    - 为了不触发 PFC，拥塞控制刻意把队列压得很低，于是买来的大缓冲主动闲置。
    - 要么像 HPC 那样，用浅缓冲把无损做彻底；要么改用有损方案，让这些缓冲真正用于吸收突发。RoCE 数据中心卡在两者之间，两头的好处都没有拿全。
- header
  - header比较复杂，开销比较大
- 对用户自定义协议支持弱
  - 对于UDP，用户可以在上面定制QUIC等协议，可以基于特定的消息流特征自定义协议。但是RoCE不支持，例如，就算这个消息到达的顺序不重要，RoCE还是会给你按照顺序送达。
- 安全性
- 链路层的可靠性
  - 这应该是一个通用的问题，不仅仅是RoCE
  - 链路层的速度提升上去以后，出错的概率也提升了。用FEC(forward error correction)的时候会有一定的等待开销与计算开销。等待开销是说，一定要收齐了一段数据以后才可以开始计算纠错，计算纠错完毕了之后才可以开始转发。
- 系统
  - 一些让延迟升高的开销，会增加拥塞控制消息的延迟，缓冲使用更多，从而进一步提升链路延迟。
